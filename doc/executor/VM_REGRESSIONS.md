# VM performance regressions against the operator tree

The shapes where the VM runs slower than the operator tree, what causes each,
and where its fix stands. The operator tree is the baseline the VM replaces
(`doc/adr/0007-one-engine-the-bytecode-vm.md`), so a regression is fixed in the VM; no
executor remains to route the shape to. Measured by the language-test benches (`profiling`
build, `mem` backend); a fix is recorded with
the measurement that shows it, and a row leaves this table once the VM is
within noise (±10%) of the tree.

| # | Shape | Benches | VM / tree | Cause | Status |

| R1 | `ORDER BY … LIMIT` | `scans/order_by_score_desc`, `computed/order_limit [stored]` | 5.5–6.1× → 1.15–1.24× | Every row reached the sort sink and was decoded whole. The sort now drops a row whose keys do not order before the last row it keeps (its floor) before gathering its keys, prunes at a quarter over what it keeps so the floor stays tight, and holds a record read in place as its stored bytes, decoded only if it keeps its place | fixed as a regression; what is left is the sort path's own cost (~0.55 ms over the scan, against the tree's ~0.35 ms), since the in-place scan itself is now within 1.05×. `order_limit_throughput`, release, 10k rows: `ORDER BY score DESC LIMIT 100` VM 6.35 ms → 1.08 ms (tree 0.92 ms); `LIMIT 10 START 5` VM 6.14 ms → 0.97 ms (tree 0.87 ms), with R4's field slot hints |
| R2 | Statements in a `FOR` loop | `create_named_table_1000`, `upsert_named_1000`, `crud/loop_create_1000`, `crud/loop_upsert_1000` | 3.5–6.1× → 0.94–1.01× (1.5–2.8× faster than legacy) | Each iteration planned the body afresh. A block is now control flow in the physical plan (`Seq`, `Let`, `For`, `Return`, `Break`, `Continue`) lowered into one program — a loop is an iterator slot and a jump, `BREAK`/`CONTINUE` are jumps — whose statements are groups of the program's own pipelines, run over its one `State` with their paging, sorts, aggregates and write state started afresh per reach; `LET` and `FOR` names are slots of the state. A write reached again in the same epoch takes the catalog reads of its earlier reaches — each table's definitions its write contexts read, its gate's answers, its stage programs — rather than reading the catalog per iteration. What is left per iteration is the statement's own execution: the per-record write path, compiling the write's clauses into its fresh contexts, its permission frames, and binding the loop parameter in a child frame, which a write's instructions read | fixed. `write_throughput` (release, best of 5, three runs), VM (tree, legacy): `crud/loop_create_1000` 5.76–5.85 ms (6.11–6.22, 16.3–16.4), was 6.58–6.78; `crud/loop_upsert_1000` 11.92–12.18 ms (11.95–11.99, 18.9–19.1), was 12.34–12.90; `FOR … CREATE t` 5.02–5.06 ms (5.31–5.37, 8.86–9.00); `FOR … UPSERT type::record` 11.48–11.61 ms (11.35–11.51, 17.1–17.3). A region now takes a body that pages its rows to the output (`region::paged_admits`): each batch runs its rows as taken, but for those `START` is sure to skip, and records how each ended, and the ordered merge replays `START` and `LIMIT` as the serial run counts them, raising a failure only for a row the serial run reaches; once the limit is spent the batches after it are dropped, their workers aborted, and the source read no further. A region's batches also run a statement nested per row that only reads, over the batch's own state; one kept from its first evaluation still runs serially. ## Fusion

A census of adjacent instruction pairs over every program the language suite
lowers (about 11 million pairs, counted statically) picks the superinstructions
`fuse::fuse` forms after lowering: a comparison and the branch on it
(`JumpIfCompare`, `JumpIfFieldInt`), a new object and the fields set on it
(`BuildObject`), and a row handed on with the row's end (`EmitEnd`). The
largest pattern the census found is a record's chain of write instructions,
each its own host step; that is R3's lever.

Release, 10k rows, after fusion (VM / tree): a plain in-place filter 1.05×
(0.595 / 0.569 ms), was 1.18×; the unindexed range filter 0.89×; the equality
filter 0.92×; R5's projections 0.99× (static) and 1.05× (opaque).
