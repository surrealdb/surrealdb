# VM hot-path shapes

The shapes where the VM's cost is decided by one mechanism, what that mechanism is, and which
benches guard it. A slowdown in any of them is fixed in the VM (`doc/adr/0007-one-engine-the-bytecode-vm.md`);
no other executor exists to route the shape to. Measured by the language-test benches (`profiling`
build, `mem` backend).

| # | Shape | Benches | Mechanism | Status |
|---|---|---|---|---|
| R1 | `ORDER BY … LIMIT` | `scans/order_by_score_desc`, `computed/order_limit [stored]` | The sort sink drops a row whose keys do not order before the last row it keeps (its floor) before gathering its keys, prunes at a quarter over what it keeps so the floor stays tight, and holds a record read in place as its stored bytes, decoded only if it keeps its place. Field reads use R4's slot hints | The cost beyond the scan is the sort path's own: the floor comparison and the pruning pass |
| R2 | Statements in a `FOR` loop | `create_named_table_1000`, `upsert_named_1000`, `crud/loop_create_1000`, `crud/loop_upsert_1000` | A block is control flow in the physical plan (`Seq`, `Let`, `For`, `Return`, `Break`, `Continue`) lowered into one program: a loop is an iterator slot and a jump, `BREAK`/`CONTINUE` are jumps, and its statements are groups of the program's own pipelines, run over its one `State` with their paging, sorts, aggregates and write state started afresh per reach. `LET` and `FOR` names are slots of the state. A write reached again in the same epoch takes the catalog reads of its earlier reaches (each table's definitions its write contexts read, its gate's answers, its stage programs) instead of reading the catalog per iteration | The per-iteration cost is the statement's own execution: the per-record write path, compiling the write's clauses into its fresh contexts, its permission frames, and binding the loop parameter in a child frame, which a write's instructions read |
| R3 | The per-record write path | `crud/update_1000`, `crud/delete_1000`, `mutate/*`, `permissions/update_scan`, `insert_1000`, `relate_1000` | A record's run of write instructions is taken in one host step. A view is bound once per table per plan, and not at all for a table with nothing to derive or guard. A `Param` makes its guard's arc-swap cell only when it compiles a guard | One host step per record |
| R4 | Unindexed filter on stored fields | `scans/where_integer_gte_lte_full [unindexed]`, `scans/where_integer_eq_full [unindexed]` | A field read probes the slot the field held in the last record first (`FieldName::slot`) and falls back to searching the stored record's keys; the record's fields are walked once per row | Guarded |
| R5 | Projection over a table with computed fields and a field guard | `computed/select_projected [opaque]`, `[static]` | Each column that carries a computed field or a field guard takes a host step | Within noise; the residual per-row cost is not attributed to a single step |
| R6 | Smaller shapes | `computed/order_limit [computed]`, `where_string_eq_order_desc_full [unindexed]` (sorts, R1's); `crud/create_1000*` (the write path, R3's) | Owned by R1 and R3 | See R1, R3 |
| R7 | The storage stages of a write: `RELATE`, indexed insert, update and delete | `zz_census/relate_1000`-shaped `write_throughput` relate, `write_throughput` indexed and `UNIQUE` insert, update and delete | A record is encoded from its marker and post-image where they are (`codec::encode_record`). The marker's common shapes are built once, and every `optimised` payload and offset table is written in place and patched, byte for byte what the Rust codec writes. B-tree and `UNIQUE` index maintenance are instructions | Guarded |
| R8 | Multi-hop and filtered graph lookups over dense graphs | `graph/two_hop [dense]`, `graph/filtered [dense]`, `graph_limit_throughput` | A lookup-bearing projection over many rows runs as morsels. A pipeline that pages its rows to the output also runs as morsels (`placement::Policy::plan`): each morsel runs its rows as taken, but for those `START` is sure to skip, and records how each ended, and the ordered merge replays `START` and `LIMIT` as a serial run counts them, raising a failure only for a row the serial run reaches. Once the limit is spent the morsels after it are dropped, their workers aborted, and the source read no further. The rows in flight are bounded by the rows the paging still needs, scaled by the share of rows that have reached it. A graph hop visits a never-folded adjacency in the cursor's buffer, as `GraphEdgeScan` does, so morsel workers do not contend on the system allocator's lock for a per-origin batch. A pipeline's morsels also run a statement nested per row that only reads, over the morsel's own state; one kept from its first evaluation runs serially | Guarded; without a `LIMIT` the pipeline's own width is the residual |

## Fusion

A census of adjacent instruction pairs over every program the language suite lowers, counted
statically, picks the superinstructions `fuse::fuse` forms after lowering: a comparison and the
branch on it (`JumpIfCompare`, `JumpIfFieldInt`), a new object and the fields set on it
(`BuildObject`), and a row handed on with the row's end (`EmitEnd`). The largest pattern is a
record's chain of write instructions, which R3 takes in one host step.
